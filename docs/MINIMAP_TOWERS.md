# 小地圖判斷「哪座塔」：2025 Worlds Finals（1080p）驗證結果

2026-10-15。資料：Worlds 2025 決賽 G1–G5，YouTube 官方轉播 1080p60 VOD；答案參照：官方 feed（塔數、確切事件時間、水晶事件）。

## 做法

1. 站點表：用 G1 開局 60 秒的小地圖建立 28 個固定站點（22 座塔、6 個水晶）。同一轉播版型下位置固定，換解析度時乘上倍率（720p→1080p 為 1.5）。
2. 模板：60 張畫格中，隊伍顏色遮罩出現比例 >= 50% 的像素。
3. 逐秒 IoU：當下遮罩 vs 模板，±3px 偏移取最大。
4. 判斷：20 秒窗口中位數 >= max(0.7 × 自己的基準, 0.25) 才算「存在」；塔不會重生，取「最後存在時間」；依序對到 feed 該隊的事件。
5. 參數只在 G1、G2 上選（試了 FRAC=0.5/0.6/0.7，取 0.7）後凍結。

## 已確認的失敗模式

1. **比賽結束假訊號**：結束時小地圖淡出，所有站點在同一秒「消失」（G3 紅 4 座、G4 藍 9 座、G2 藍 2 座）。需要用 feed 的結束時間排除，否則數量全錯。
2. **存活但分數漂移**：G5 的 R_top_outer 從 0.4–0.5 緩降到 0.25–0.31（沒有掉到 0，feed 說還活著），被判成消失。
3. **低基準外塔**：外塔（outer）的基準常只有 0.2–0.4，辨別力差，G5 藍方漏 3 座。
4. **相近事件的順序互換**：G1（18:19／20:37）、G3（29:23–30:30 三件在 70 秒內）無法排出可靠順序。
5. **英雄站在塔上造成短暫假「存在」**，最長 +145 秒。

## 嘗試過但無效

- 覆蓋率指標（不扣多餘像素）：比 IoU 差。
- 絕對低值門檻（20 秒中位 <= min(0.15, 基準/2)）：漏判變多，比較差，已放棄。
- 直接用 720p：只有 3/10 事件能對上。

## 還沒有的

- 沒有獨立的標準答案可以逐座核對「事件→塔名」，只有 feed 數量、路線順序、水晶事件時間三種一致性檢查。
- 運算成本未量測。
- 基地塔、第 12 件事件（G2）沒有可靠判斷。

## 目前能說的

- 「塔有幾座」：官方 feed 即可，已驗證。
- 「是哪一座」：在訊號乾淨時（例如 G4 紅方 9 座全部抓到、水晶時間吻合）可以給出，但在 G3、G5 會漏、會多、會排錯順序，不能當成穩定功能；建議附信心度，不確定時留空。

## 第二輪（2026-10-15）：鍍層模板 + 事件驅動

### 新發現：外塔圖示在約 14:00 會改變

畫面核對（G2 的 R_top_outer、R_bot_outer、B_top_outer）：12:55 時外塔圖示帶有紫色／藍色的鍍層標記，15:20 變成單純的塔圖示；內塔（R_top_inner）沒有變。第一輪的模板取自遊戲第 7–8 分鐘（鍍層還在），所以外塔的基準偏低、分數漂移，這是外塔在每一場都表現差的主因，不是門檻問題。

修正：模板改取 G1 的 14:16–15:56（鍍層消失後、第一座塔倒下前，100 秒）。

### 方法（v6）

- feed 給確切事件時間 v；對該隊每個還存活、符合路線順序的站點：
  - pre = v-60..v-8 內 10 秒中位數的最大值（>= 0.18 才有資格）；
  - 下降須在 v±12 秒內發生（先降到 pre 的一半以下，之後 22 秒中位仍 <= 60%）；
  - 分數 = pre - max(v+6..v+40 的中位, v+40..v+150 的中位)，>= 0.12 才指派；第一名與第二名差 >= 0.08 標「確定」，否則「接近」，無則「不確定」。

### 已確認的失敗模式（新增）

6. **英雄站在自己的塔上守塔**：G2 的 R_mid_outer 被紅方英雄蓋住 16:10–16:40，造成持續 2 分鐘的低分，符合「下降後持續低」的條件，被誤判成消失。

### 尚未做、建議的下一步

- 「塔不會重生」的否決：事件之後只要出現過一次強存在證據（例如 5 秒中位 IoU >= 0.55），該站點就不能是這個事件的塔。這比「後 150 秒中位數」更能擋掉守塔英雄造成的持續低分。
- 基地塔只允許在該隊第一個水晶事件之後被指派。
- 把 pre 的門檻提高到 0.4 以上，擋掉外塔底噪（0.2 左右）造成的假存在。

## 第三輪（2026-10-15）：灰階 NCC + 路線前綴動態規劃，準決賽驗證

### 關鍵改動

1. **特徵改成灰階外觀 NCC**（取代顏色遮罩 IoU）。模板 = G1 鍍層消失後 100 秒的逐像素中位數，15×15，±6px 搜尋。存活約 0.9–0.99，消失約 0.4–0.55（遮擋時也會落在 0.3–0.5，和消失重疊，只能靠「塔不會重生」的長時間序列排除）。開發集五場所有塔的存活基準都 >= 0.83（IoU 時代外塔只有 0.2–0.4）。
2. **路線前綴 + 動態規劃**：每一路被摧毀的塔必為（外 → 內 → 水晶塔）的前綴，所以每個事件只需決定「哪一路」；以 (上、中、下、基地塔) 各已倒幾座為狀態，精確求全局最佳解。基地塔只允許在該隊第一個水晶事件之後。
3. 站點座標以開局底圖的圖示重心重新校準（多數只差 0.6–2.4 像素，B_bot_outer 差 4.5）。

### 逐件畫面核對（系統性抽樣：每局被指派的事件隔一件取一件，共 25 件；核對者為我本人，非盲測）

- 正確（事件前看得到塔、事件後持續消失）：9
- 偏可能（事件前被英雄或畫面遮住，事件後持續消失）：9
- 無法判定（畫面全黑或比賽結束）：3
- **錯：4**（S1 24:21 B_mid_inner、S3 15:57 R_mid_outer、S3 24:31 R_bot_inner、S4 28:51 B_mid_outer）。共同點：事件後 25 秒塔還在，之後才消失。
- 可判定的 22 件中，正確或偏可能 18 件 = **82%**；兩端都看得見的嚴格正確 9/22 = 41%。

### 新發現：feed 事件時間戳不能信到 ±10 秒

- 影片的 HUD 遊戲時鐘與影片時間全程同步（S1 在 clip 1505→2800 秒，時鐘前進 1295 秒對影片 1295 秒；S3 同樣），所以不是影片對時的問題。
- 以「NCC 銳利且持久的下降」當錨點，影片裡塔消失的時間與最近的 feed 事件相差 **−45 到 +45 秒**（31 個錨點，中位數 −6 秒），雙峰：一群在事件前 10–25 秒、一群在事件後 20–45 秒。
- 例：S1 的 B_mid_outer 與 B_mid_inner 在影片 25:07 同時消失，feed 的事件是 24:11 與 24:21（晚了 45–55 秒）；S4 的 29:26 有三座塔在 2 秒內一起消失。
- 推測（未驗證）：feed 的事件時間戳有可變延遲或批次延遲。**feed 的「計數」仍可信，「時間」不可信到秒級。**
- 因此前面的「事件驅動」假設（以 feed 時間定位事件）有結構性誤差，這是 4 件錯誤的主因，不是模板或門檻。

### 最終狀態檢查（比賽結束時，NCC 持續消失的塔數 vs feed 事件數）

18 個「局 × 隊」中 7 個完全一致，其餘大多差 1 座（G1 紅、G3 紅、G4 紅、S1 紅藍、S2 紅），S3 紅差很多（偵測 3 vs feed 8）。基地塔一座都沒偵測到（基地圖示 NCC 判斷未做）。

### 下一步建議

- **不再用 feed 時間定位**，改成：從影片 NCC 找每座塔「最後存在證據」與「持續消失」的區間，依時間排序後與 feed 事件的**順序**（不是時間）對應；feed 只提供各隊總數與「發生過幾件」。
- 以第三組沒看過的系列（例如八強賽 T1 3–2 AL，5 局）驗證，不再調參。

## 第 4 輪：三狀態分類器 + 觸發式命名 + 八強盲測（2026-10-15）

- 分類器：A 存活 / D 消失 / O 遮擋，SVM(RBF)，503 維特徵（灰階 14×14、H/S/V 9×9、Sobel 8×8）。標註 520 張（A370 / D85 / O56 / 未判 9），標註者是我（Claude），不是盲標。
- 評估：留一場交叉驗證 93.3%；準決賽 160 張獨立測試 92.3%。O（遮擋）召回只有 50–62%，是主要弱點（英雄頭像壓在塔上會被誤判成存活）。
- 命名規則（凍結）：每秒每站點取 P(A)/P(D)（門檻 0.7）；連續存活 ≥4 秒重置、累計消失 ≥8 秒且目前不存活才成為候選；feed 塔數（含 20 秒領先模擬）為上限；路線前綴約束（外塔→內塔→水晶塔；主堡塔需先有該隊水晶被破）；連續存活 ≥5 秒則撤銷（塔不會重生）；結束時以最低存活機率補滿 feed 缺額（≤0.5 才補）。
- 準決賽終局圖核對：可驗證的已命名塔 41/41 正確；補滿後塔數與 feed 一致 8/8 隊局。
- 八強盲測（參數未改，q3 / q5；q1 q2 q4 下載 HTTP 403 沒有資料）：
  - q3：紅 feed 5 / 命名 5；藍 feed 6 / 命名 6。命名延遲中位數 11 秒、最大 125 秒。
  - q5：紅 feed 3 / 命名 3；藍 feed 9 / 命名 9。命名延遲中位數 9 秒、最大 27 秒。
